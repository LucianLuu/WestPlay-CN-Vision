# QQ 音乐只能播 30 首 —— 问题与修复

**日期**：2026-11-26
**版本**：3.0.2
**现象**：玩家报「QQ 音乐歌单能完整显示，但播到第 31 首会跳回第 1 首」

---

## 一、结论先说

一个数字写死了：**`num=30`**。

代码向 QQ 音乐的中间层要歌单时，把「每页 30 首」写在了 URL 里，而调用方以为拿到的是整张歌单。
于是播放器记下的队列只有 30 首，`Next` 到第 31 首就绕回第一首。

修了两处，任一处都能解决问题，两处都留着了。

---

## 二、链路是怎么走的

先看一条命令从「点歌」到「出声」经过谁：

```
玩家点歌单里的第 31 首
    ↓
ui/src/cabin/apps/qq/qqMusic.ts   playFrom(context, tracks, index)
    ↓  postMessage
crates/host/src/qq_music.rs       原样转发（Command::Play）
    ↓  PostWebMessageAsJson
crates/host/src/qq_music.js       眼前的这个隐藏页面
    ↓  页面自己的 CONTROLS.play(msg)
QQ 中间层（Python，run.pyc）       记住队列，一条条播
```

**关键**：队列是**账户侧（Python 层）**维护的。应用只是告诉它「放什么」，之后 `Next` 只发一个
`{action:'next'}`，不再带列表 —— **队列在层里，层记多少就播多少**。

---

## 三、问题出在哪

### 3.1 第一个坑：`songsOfList` 里写死了 `num=30`

`crates/host/src/qq_music.js`，改之前：

```js
const songsOfList = async (id, kind) => {
  const text = String(id ?? '')
  const numeric = /^\d+$/.test(text)
  const route =
    kind === 'top'
      ? `/top/${encodeURIComponent(text)}/detail?num=30`          // ← 写死
      : numeric
        ? `/songlist/${encodeURIComponent(text)}/detail?num=30`    // ← 写死
        : kind === 'artist'
          ? `/singer/${encodeURIComponent(text)}/songs?num=30`     // ← 写死
          : `/album/${encodeURIComponent(text)}/songs?num=30`      // ← 写死
  const found = await get(route)
  const songs = found.songs ?? found.song_list ?? []
  return songs.map((song) => song?.mid).filter(Boolean)
}
```

**四个分支全是 `num=30`。** 不管歌单有 30 首还是 500 首，这里只要回来 30 个 id。

同一个文件里明明有能翻页的 `fetchAllSongs`（应用自己显示歌单列表时用的就是它）：

```js
const MAX_PAGES = 10
const fetchAllSongs = async (path, key = 'songs') => {
  for (let page = 1; page <= MAX_PAGES; page += 1) {
    f = await get(`${path}${path.includes('?') ? '&' : '?'}num=100&page=${page}`)
    ...
```

**每页 100 首、最多 10 页（1000 首）、翻到空为止** —— 显示列表时拿的是全的。只有「播」这条路
走了 `songsOfList`，于是短了一截。

### 3.2 第二个坑：点歌单里的歌时只发 `id`，不发列表

`ui/src/cabin/apps/qq/qqMusic.ts`，改之前：

```ts
if (isInHost()) {
  const list = !context
  qqMusic({
    action: 'play',
    ...(list
      ? { songs: tracks.map((track) => track.id) }    // 无 context：发完整列表
      : { id: context.id, kind: context.kind }),       // 有 context：只发 id ← 歌单走这里
    index: start,
    shuffle: shuffled,
  })
}
```

`context` 就是「从哪个歌单/专辑点的」。**从歌单里点歌时 `context` 有值，于是只发了 `id`。**

层收到 `id` 之后怎么做？`qq_music.js` 的 `CONTROLS.play`：

```js
async play(msg) {
  const ids = (msg.songs ?? []).filter(Boolean)
  if (ids.length > 0) {
    player.queue = ids                                   // ← 有列表就直接用，这是对的
    player.index = Math.min(msg.index ?? 0, ids.length - 1)
  } else if (msg.id) {
    let list = await songsOfList(msg.id, msg.kind)       // ← 没列表才自己查，撞上 3.1
    ...
```

**层自己的逻辑是完整的** —— 有 `songs` 就用；没有才去查。问题是应用从来没给。

### 3.3 两个坑叠在一起

```
点歌单里的歌 → 只发 id → 层自己查 → songsOfList 写死 num=30 → 队列 30 首
                                                            ↓
                                              播到第 31 首，绕回第 1 首
```

## 四、怎么修的

### 4.1 `songsOfList` 改成走分页

```js
const path =
  kind === 'top'
    ? `/top/${encodeURIComponent(text)}/detail`
    : numeric
      ? `/songlist/${encodeURIComponent(text)}/detail`
      : kind === 'artist'
        ? `/singer/${encodeURIComponent(text)}/songs`
        : `/album/${encodeURIComponent(text)}/songs`
const { songs } = await fetchAllSongs(path, numeric || kind === 'top' ? 'songs' : 'song_list')
return songs.map((song) => song?.mid).filter(Boolean)
```

把 `num=30` 从 URL 里去掉，交给 `fetchAllSongs` —— 它自己拼 `num=100&page=N`，翻到空为止。
和应用显示列表用的是**同一条路**，不会再有「看到的和播到的不是一个列表」这种事。

### 4.2 应用直接把自己手里的列表交出去

```ts
// `songs` alone, no `id`: the layer takes a list as given, but asked for a playlist by id it
// reads the list itself — and stops at 30.
qqMusic({
  action: 'play',
  songs: tracks.map((track) => track.id),
  index: start,
  shuffle: shuffled,
})
```

改成**永远发完整 `songs` 数组**，不再发 `id`。

理由：应用点进歌单时**本来就把整张列表拉下来了**（显示用的就是它），直接交给层最省事，
也不依赖层怎么查。

### 4.3 为什么两处都留着

| | 4.1（`songsOfList` 分页） | 4.2（应用发完整列表） |
|---|---|---|
| 覆盖场景 | 任何「按 id 播放」的路径 | 应用点歌单/专辑时 |
| 依赖 | 层的分页行为 | 无（用自己已有的数据）|

4.2 是更稳的那条 —— 数据已经在手里，不用再问一次。4.1 保证别的调用方（比如以后新增的入口）
不会再踩同一个坑。

## 五、顺带发现的一件事（没修，记在这里）

层的 `/songlist/{id}/detail` **不返回 `total_num` 也不返回 `hasmore`**。实测一个 299 首的歌单：

```
page 1: 100 首
page 2: 100 首
page 3:  99 首      ← 到这儿应该完了
page 4: 100 首      ← 但继续问还有
page 5:  96 首
```

第 4、5 页的 song mid **和前面不重复**（查过，495 个唯一 mid），所以不是循环返回 ——
更像是接口对越界的页码也不报错，继续给数据。

结果：`fetchAllSongs` 只能靠「空页」停，实际会多要几页。**不影响播放**（多的歌排到队尾），
但列表长度可能比歌单真实长度大。要精确的话得看层能不能补上 `total` 字段，那是 Python 层
（`run.pyc`，非开源）的事。

## 六、怎么验证修好了

1. 打开 QQ 音乐，进一个 **30 首以上**的歌单（备注里带「100首」「精选」那种一般够）
2. 从列表里点第 31 首（或任意一首）
3. 让它自然播完，或按「下一首」

**修好**：能顺着往下走，不会回到第 1 首。
**没修好**：第 31 首之后又回到开头。

想看队列多长，用调试端口连上 QQ 音乐页面（见 3.0.0 交接文档「诊断开关」一节）：

```js
// 队列长度
document.querySelector('audio') ? 'playing' : 'paused'
```

## 附：给以后的人

**看到写死的分页数字要警惕。** 这个 bug 活了很久，因为：

- 列表能完整显示（走的是 `fetchAllSongs`）
- 界面、日志、错误提示一切正常
- 只有「播到第 31 首」这一个瞬间才暴露

而且 30 这个数字不显眼 —— 很多歌单本来就不足 30 首，看过去一切正常。

**同一个动作有两个实现时，迟早会不一致。** 显示列表和播放列表本来就是同一个列表，
应该走同一条查询路径（现在就是）。
